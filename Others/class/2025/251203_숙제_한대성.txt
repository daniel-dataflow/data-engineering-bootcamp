데이터 베이스에서 index란 무엇인가? 왜 추가하면 self join에서 빨라지는 이유는?

**1. 인덱스(Index)란 무엇인가?**

인덱스는 데이터베이스 테이블에 있는 데이터를 빠르게 찾기 위해 별도로 구성한 **자료구조**입니다.
• **기본 개념:** 책의 맨 뒤에 있는 '색인(Index)'과 동일한 원리입니다. 책의 내용을 처음부터 끝까지 다 읽는 것(Full Table Scan) 대신, 색인에서 키워드를 찾아 해당 페이지로 바로 이동하는 방식입니다.
• **기술적 실체 (B-Tree):** 대부분의 관계형 데이터베이스(RDBMS)는 인덱스를 관리하기 위해 **B-Tree(Balanced Tree)** 또는 **B+Tree**라는 자료구조를 사용합니다. 이 구조는 데이터가 항상 정렬된 상태를 유지하도록 하여, 탐색 시간을 획기적으로 줄여줍니다.Shutterstock**핵심 팩트:**
• 인덱스가 없으면 데이터베이스는 데이터를 찾기 위해 테이블 전체를 순차적으로 뒤져야 합니다 (**Full Table Scan**).
• 인덱스가 있으면 정렬된 트리 구조를 타고 내려가 원하는 데이터를 즉시 찾습니다 (**Index Seek/Scan**).

**2. Self Join에서 인덱스가 속도를 높이는 이유**

Self Join은 하나의 테이블을 두 번(마치 다른 테이블인 것처럼) 사용하여 서로 연결하는 작업입니다. 주로 `직원-매니저` 관계나 `카테고리-상위 카테고리` 같은 **계층형 데이터**를 조회할 때 사용됩니다.
인덱스가 추가되었을 때 빨라지는 이유는 데이터베이스가 조인을 수행하는 알고리즘인 **중첩 루프 조인(Nested Loop Join)** 의 효율성이 완전히 달라지기 때문입니다.

**A. 인덱스가 없을 때 (느린 이유)**

인덱스가 없으면 데이터베이스는 최악의 경우 $O(N^2)$의 복잡도로 작동합니다.
1. **Outer Loop:** 첫 번째 테이블(A)의 첫 번째 행을 읽습니다.
2. **Inner Loop:** 연결할 짝을 찾기 위해 두 번째 테이블(A')을 **처음부터 끝까지 스캔(Full Table Scan)** 합니다.
3. 이 과정을 A테이블의 모든 행(N개)에 대해 반복합니다.
• **결과:** 만약 데이터가 10,000개라면, `10,000 * 10,000 = 1억 번`의 연산이 발생할 수 있습니다.

**B. 인덱스가 있을 때 (빨라지는 이유)**

조인 연결고리(Join Key, 예: `parent_id`)에 인덱스가 있다면 복잡도가 $O(N \log N)$으로 급격히 감소합니다.
1. **Outer Loop:** 첫 번째 테이블(A)의 첫 번째 행을 읽습니다.
2. **Inner Loop:** 연결할 짝을 찾기 위해 두 번째 테이블(A')의 전체를 뒤지는 대신, **인덱스 트리(B-Tree)를 타고 내려가 위치를 바로 찾습니다(Index Seek).**
3. 트리 탐색은 데이터가 많아져도 단계가 거의 늘어나지 않습니다.
• **결과:** 데이터가 10,000개라도 인덱스(B-Tree)의 높이가 약 3~4단계라면, `10,000 * 4 = 4만 번` 정도의 연산으로 끝납니다. (1억 번 vs 4만 번의 차이)

**3. 성능 비교 및 검증 데이터**

데이터베이스 엔진(Optimizer)이 실제로 수행하는 작업의 차이를 표로 정리했습니다.**비교 항목인덱스 없음 (Non-Indexed)인덱스 있음 (Indexed)조인 방식**Inner Table에 대해 **Full Table Scan** 수행Inner Table에 대해 **Index Seek** 수행**시간 복잡도**$O(N^2)$ (기하급수적 증가)$O(N \log N)$ (완만항 증가)**I/O 부하**디스크의 모든 블록을 반복해서 읽음 (Random I/O 폭증)필요한 블록만 콕 집어서 읽음**적합한 상황**데이터가 매우 적을 때 (수백 건 이하)**대부분의 실무 환경 (수천 건 이상)**기술적 참고 (Advanced Note):
최신 DB 옵티마이저는 데이터가 매우 많고 인덱스가 없는 경우, 강제로 Hash Join이라는 방식을 사용하여 $O(N^2)$를 피하려고 시도하기도 합니다. 하지만 계층형 데이터(Self Join)에서는 인덱스를 통한 Nested Loop Join이 가장 안정적이고 빠른 응답 속도를 보장하는 것이 검증된 사실입니다.

**BCNF**

BCNF(Boyce-Codd Normal Form)는 데이터베이스 정규화의 한 단계로, 3NF(제3정규형)보다 더 엄격한 조건을 요구하는 정규형입니다.
제 3정규형보다 조금 더 엄격한 제약 조건을 가지기 때문에 Strong 3NF라고도 한다.

BCNF 정규형을 만족하려면 아래 조건을 만족해야한다.
1. 제 3정규형(3NF)을 만족해야한다.
2. 모든 결정자(determinant)가 후보 키(candidate key) 집합에 속해야한다.
=> 속성 A가 속성 B를 결정하면, A는 후보 키여야 한다.

BCNF 정규화의 필요성
1. 데이터 중복 제거
BCNF를 적용하면 불필요한 데이터 중복을 최소화할 수 있습니다.
교수와 강좌 정보가 하나의 테이블에 있으면 같은 강좌에 대해 반복적으로 교수 정보를 기록해야 하는데, BCNF로 분리하면 이러한 중복을 방지할 수 있습니다.

2. 이상 현상 제거
삽입, 삭제, 갱신 시 발생하는 이상 현상을 제거할 수 있습니다.
새로 강좌를 추가하려고 할 때 해당 강좌에 교수 정보가 없다면 삽입할 수 없는 상황이 생길 수 있는데, BCNF로 정규화하면 이러한 문제를 해결할 수 있습니다.

3. 결정자 (Determinant)
다른 속성을 결정하는 역할을 하는 속성 또는 속성집합입니다.
결정자는 항상 유일해야하며, BCNF에서는 이 결정자가 반드시 후보키여야합니다.

4. 후보키 (Candidate Key)
테이블의 각 튜플(행)을 유일하게 식별할 수 있는 속성 또는 속성집합입니다.
하나의 테이블에는 여러 후보키가 있을 수 있으며, 그중 하나는 기본키(Primary Key)로 선택됩니다.
